# 志愿者状态跟踪表

本文件用于跟踪 2026 大会正式志愿者从确认加入项目到活动现场执行前的整体准备状态。

> 本表只记录项目协作所需的非敏感信息。
>
> 身份证、银行卡、家庭住址、详细健康信息、候选人内部评价等内容不得记录在本文件中。

---

## 一、文件用途

本文件主要回答：

> **每一名正式志愿者目前准备到哪一步？**

它与其他人员文件的区别：

    volunteer-status.md
    = 这个人准备到哪一步

    availability.md
    = 这个人哪些日期可以参加

    docs/03-schedule/
    = 负责人最终安排这个人哪天工作

三者不得混淆。

---

## 二、成员准备流程

正式志愿者整体状态按照以下流程推进：

    待邀请
       ↓
    已邀请
       ↓
    已加入
       ↓
    入组完成
       ↓
    培训完成
       ↓
    待排班
       ↓
    已排班
       ↓
    岗位确认
       ↓
    READY

其中 `READY` 表示：

> 活动前要求已经完成，成员具备进入现场执行阶段的条件。

---

## 三、主要状态说明

| 状态 | 含义 |
|---|---|
| 待确认 | 部分关键信息尚未确认 |
| 待邀请 | 已确认参与，等待发送 GitHub 邀请 |
| 已邀请 | GitHub 邀请已经发送，等待成员接受 |
| 已加入 | 已成功进入项目协作空间 |
| 入组完成 | 已完成规定的入组流程 |
| 培训中 | 已开始培训，但尚未完成 |
| 培训完成 | 已完成负责人要求的培训 |
| 待排班 | Availability 已确认，等待正式安排 |
| 已排班 | 正式工作日期已经确定 |
| 岗位确认 | 正式岗位及工作区域已经明确 |
| BLOCKED | 当前存在阻塞问题，暂时无法继续推进 |
| READY | 活动前全部必要准备已经完成 |

## 八、READY 判定标准

只有同时满足以下条件，最终状态才可以更新为 `READY`：

- [ ] GitHub Username 已确认
- [ ] 项目访问权限正常
- [ ] Volunteer ID 已确认
- [ ] 入组流程已完成
- [ ] Availability 已确认
- [ ] 必要培训已完成
- [ ] 正式排班已确认
- [ ] 岗位已确认
- [ ] 工作区域已确认
- [ ] 集合时间已知晓
- [ ] 集合地点已知晓
- [ ] 对应负责人已知晓
- [ ] 现场沟通方式已知晓
- [ ] 异常升级流程已知晓

全部满足后：

> **最终状态：READY**

## 九、BLOCKED 使用规则

如果成员因为某个问题暂时无法继续推进，可以使用：

`BLOCKED`

例如：

- GitHub 邀请无法接受
- 项目访问权限异常
- Availability 存在重大冲突
- 培训未能完成
- 正式排班存在无法解决的冲突
- 其他影响 READY 的问题

使用 `BLOCKED` 后，负责人应同时明确：

    问题是什么
       ↓
    谁负责处理
       ↓
    下一步行动
       ↓
    预计什么时候解决

不能只标记 `BLOCKED` 而不处理。

其中：

### People & Scheduling

- Volunteer ID

- 培训状态
- Availability

### Operations

主要提供：

- 岗位确认结果
- 工作区域确认结果

### Project Lead

主要负责：

- 检查关键 BLOCKED 项
- 组织最终 READY Review
- 协调跨模块问题

## 十一、成员发现信息错误

普通志愿者如果发现自己的状态错误，例如：

- GitHub Username 错误
- Availability 错误
- 培训状态错误
- 排班状态错误
- 岗位状态错误

应联系对应负责人。

后续 Issue 模板上线后，可以使用：

`[支持请求]`

或：

`[排班调整]`

提交。

不建议普通志愿者直接修改其他成员的状态。

---

## 十二、Availability 更新联动

如果：

`roster/availability.md`

发生变化，负责人需要判断是否影响本表。

例如：

    V008
    Availability：已确认

变成：

    Availability：需协调

如果此人已经正式排班，则：

    Availability 变化
          ↓
    检查正式排班
          ↓
    判断是否需要调整
          ↓
    更新 Schedule
          ↓
    更新本表最终状态

不能只修改 Availability，而不检查正式排班。

---

## 十三、排班更新联动

成员进入正式排班后，应同步更新：

`排班：已确认`

如果排班随后发生变更：

`排班：需调整`

在新的正式安排确认后，再恢复：

`排班：已确认`

如果排班问题影响活动参与，应考虑将最终状态改为：

`BLOCKED`

直到问题解决。

---

## 十四、岗位更新联动

正式岗位确认后：

`岗位：已确认`

如果大会方现场需求尚未确定，则保持：

`岗位：待确认`

这是正常状态。

不得为了让成员提前变成 READY 而虚构岗位信息。

---

## 十五、状态检查频率

筹备阶段不需要为了更新而频繁修改。

建议在以下节点统一检查：

### 正式成员确认后

检查：

- GitHub Username
- Volunteer ID
- 待邀请状态

### GitHub 邀请后

检查：

- 是否成功加入
- 是否可以正常访问

### 培训阶段

检查：

- 入组
- 培训
- Availability

### 排班阶段

检查：

- Availability
- 正式排班
- 岗位

### 活动前最终检查

检查：

- BLOCKED 成员
- 非 READY 成员
- 每日人员数量
- 岗位缺口
- 负责人缺口

---

## 十六、负责人 READY Review

活动开始前，由三位负责人进行最终检查。

重点关注：

| 检查项 | 目标 |
|---|---|
| 正式成员数量 | 20 人确认 |
| GitHub 访问 | 所需成员正常 |
| 入组 | 全部完成 |
| 培训 | 全部达到要求 |
| Availability | 全部确认 |
| 正式排班 | 所需日期全部确认 |
| 岗位 | 正式成员岗位明确 |
| BLOCKED | 关键阻塞清零 |
| READY | 当日正式成员全部 READY |

如果存在未解决的 `BLOCKED`，必须明确负责人和处理方案。

## 十八、信息安全

本表允许记录：

- Volunteer ID
- GitHub Username
- 项目状态
- 培训状态
- Availability 状态
- 排班状态
- 岗位状态

本表禁止记录：

- 身份证号码
- 身份证照片
- 银行卡信息
- 收款账户
- 家庭住址
- 密码
- 验证码
- 详细健康信息
- 候选人筛选评价
- 淘汰原因
- 其他不必要的个人隐私

敏感信息通过另外的受控方式管理。

## 十九、最终目标

本文件最终应该让三位负责人可以快速回答：

    20 名志愿者现在准备到哪一步？

    谁还没有加入 GitHub？

    谁还没有完成入组？

    谁还没有完成培训？

    谁的 Availability 还没有确认？

    谁还没有正式排班？

    谁还没有岗位？

    谁目前 BLOCKED？

    谁已经 READY？

当活动前需要的正式成员全部达到：

> **READY**

人员准备阶段即可视为完成。
