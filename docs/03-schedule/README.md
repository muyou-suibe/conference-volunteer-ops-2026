活动日期：

- 2026 年 9 月 6 日
- 2026 年 9 月 7 日
- 2026 年 9 月 8 日
- 2026 年 9 月 9 日

> 本目录中的正式排班与 `roster/availability.md` 不同。
>
> Availability 表示成员是否可以参加；
> Schedule 表示项目负责人最终安排成员在哪一天、哪个岗位工作。

## 二、排班状态

每一份每日排班必须标明状态。

统一使用：

| 状态 | 含义 |
|---|---|
| `DRAFT` | 草案，仍可能调整 |
| `REVIEW` | 负责人正在确认 |
| `FINAL` | 正式版本 |
| `CLOSED` | 当日工作已结束，排班归档 |

活动前，志愿者只能把：

**FINAL**

状态的排班作为正式工作安排。

---

## 三、排班基本原则

### 1. 先确认 Availability，再安排 Schedule

负责人安排成员前，应首先检查：

`roster/availability.md`

只有该成员对应日期为：

`✅ 可以参加`

或经过负责人确认的：

`⚠️ 有条件参加`

才可以进入正式排班。

---

### 2. 每名成员必须有明确岗位

不能只记录：

> V003 / 9 月 8 日上班

应至少明确：

- Volunteer ID
- GitHub Username
- 工作日期
- 岗位
- 工作区域
- 集合时间
- 计划开始时间
- 计划结束时间
- 对应负责人

---

### 3. 一个岗位必须有明确负责人

每名志愿者当天必须知道：

> “出现问题时，我找谁？”

因此排班表必须明确：

`Manager / 负责人`

避免现场出现无人负责的情况。

---

### 4. 正式排班以 GitHub 最新 FINAL 版本为准

微信群、私聊、口头通知可以用于即时沟通。

但如果形成正式调整，应同步更新 GitHub。

原则：

> GitHub = 正式记录  
> 即时通讯 = 实时沟通

---

## 四、每日排班必须包含的信息

每天的排班文件至少包括以下内容。

### 基本信息

- 日期
- 排班状态
- 当日计划人数
- 集合时间
- 集合地点
- 预计工作时间
- 当值负责人

### 志愿者安排

| 字段 | 含义 |
|---|---|
| ID | Volunteer ID |
| GitHub | GitHub Username |
| 岗位 | 当日主要岗位 |
| 区域 | 工作区域 |
| 集合时间 | 要求到达时间 |
| 开始 | 计划开始工作时间 |
| 结束 | 计划结束工作时间 |
| 负责人 | 当日直接负责人 |

### 备用 / 机动人员

如果当天设置机动人员，应单独列出。

---

## 五、工作时长

原则上每日工作：

**约 8 小时**

具体时间以当天正式排班为准。

正常工作报酬：

**300 元 / 天**

如实际工作产生符合规定的加班，由负责人按照项目要求进行确认。

> GitHub 仅记录工作与加班确认状态。
> 银行卡、收款账户等财务敏感信息不得进入本仓库。

---

## 六、集合规则

正式排班中应明确：

- 集合时间
- 集合地点
- 对应负责人
- 当日注意事项

原则上志愿者应提前到达，不建议将：

> 工作开始时间

直接作为：

> 到达会场时间

集合时间：08:00
