# 项目沟通与信息同步规则

本文件用于统一 2026 大会志愿者项目的沟通方式、正式信息发布规则、问题升级方式以及 GitHub 与即时通讯之间的信息同步要求。

本文件与：

`docs/00-management/responsibilities.md`

共同构成三位项目负责人的基础管理规则。

核心原则：

> **即时通讯解决速度问题，GitHub 解决正式记录问题。**

以及：

> **重要决定必须有唯一、明确、可追溯的正式版本。**

---

## 一、沟通目标

本项目的沟通体系需要保证：

- 志愿者知道应该去哪里获取正式信息
- 紧急问题可以快速找到负责人
- 三位负责人不会重复发布互相冲突的信息
- 群聊中的重要决定不会丢失
- 正式排班和岗位变化可以追踪
- 现场问题有明确升级路径
- 每项需要处理的问题都有 Owner
- 敏感信息不会错误进入公共沟通渠道

最终目标：

> 每个人都知道“什么事情在哪里说、找谁说、最终以哪里为准”。

---

## 二、沟通工具分工

本项目主要使用：

| 工具 | 主要用途 |
|---|---|
| GitHub | 正式记录、文档、任务、排班、Issue、变更、复盘 |
| 即时通讯 | 实时通知、快速确认、临时协调、紧急沟通 |
| 现场口头沟通 | 活动现场立即执行的调度和紧急问题 |

三者不是互相替代关系。

推荐理解：

    GitHub
    = 正式信息源

    即时通讯
    = 实时沟通渠道

    现场口头沟通
    = 现场快速执行渠道

---

## 三、GitHub 负责什么

以下内容原则上应进入 GitHub：

- 项目管理规则
- 负责人职责
- 入组指南
- 培训材料
- Volunteer Status
- Availability
- 正式排班
- 岗位说明
- 现场 SOP
- 项目任务
- 排班调整记录
- 重要现场异常
- 需要持续跟踪的问题
- 项目复盘

GitHub 的优势是：

> 可以看到“当前正式版本是什么”。

因此对于会影响后续执行的重要信息，不应只留在群聊中。

---

## 四、即时通讯负责什么

即时通讯主要用于：

- 集合提醒
- 培训提醒
- 活动通知
- 临时问题确认
- 人员到岗确认
- 临时调度
- 现场支援请求
- 紧急事件
- 提醒成员查看 GitHub 正式更新

例如：

> “9 月 6 日排班已经更新为 FINAL，请相关成员查看 GitHub 并确认。”

这种消息适合发送到即时通讯。

但正式排班内容本身仍然以 GitHub 为准。

---

## 五、现场口头沟通负责什么

活动现场存在大量必须立即执行的问题，例如：

- 某签到区域突然排队
- 某岗位需要临时支援
- 某成员需要暂时离岗
- 参会者流量发生变化
- 某工作区域临时调整
- 出现安全风险
- 嘉宾或大会方提出紧急需求

这类情况可以先：

    现场口头沟通
          ↓
    立即执行
          ↓
    情况稳定
          ↓
    判断是否需要正式记录

不要求所有临时口头指令都立即进入 GitHub。

但如果造成：

- 正式岗位变化
- 正式排班变化
- 人员缺席
- 重大异常
- 加班
- 重要责任变化

则应在情况稳定后补充正式记录。

---

## 六、Single Source of Truth

项目采用：

> **GitHub = Single Source of Truth**

即：

当多个渠道的信息存在差异时，原则上应检查 GitHub 中的最新正式版本。

例如：

微信群里曾经说：

    集合时间 08:30

之后负责人正式确认：

    集合时间 08:00

并已经更新 GitHub `FINAL` 排班。

那么正式安排应以：

> GitHub 最新 FINAL 版本

为准。

---

## 七、什么信息属于“正式信息”

以下内容属于正式信息：

- 正式人员名单
- Volunteer ID
- Availability 确认结果
- 正式培训状态
- 正式排班
- 正式岗位
- 集合时间
- 集合地点
- 工作时间
- 直接负责人
- 正式人员变更
- 重要岗位变更
- 重大现场异常结果
- 加班确认状态
- 项目规则

正式信息发生变化后，应更新对应 GitHub 文件或 Issue。

---

## 八、什么信息不需要全部进入 GitHub

以下内容一般不需要逐条记录：

- “收到”
- “好的”
- “我到了”
- “我去吃饭了，10 分钟回来”
- 临时问路
- 普通现场咨询
- 简短提醒
- 没有形成正式决定的讨论
- 已经立即解决且没有后续影响的小问题

原则：

> GitHub 记录需要追踪的结果，不记录所有聊天过程。

避免把仓库变成聊天记录存档。

---

## 九、正式通知发布规则

涉及全体或多人执行的重要通知，应尽量包含：

- 事项
- 适用人员
- 日期
- 时间
- 地点
- 需要执行的动作
- 信息来源
- 负责人

例如：

    【正式通知】

    事项：9 月 6 日志愿者集合

    适用人员：当天正式排班 4 人

    集合时间：TBD

    集合地点：TBD

    要求：到达后联系当天 Operations

    正式排班：GitHub 对应 FINAL 文件

这样比：

> “大家明天早点来”

更加清楚。

---

## 十、正式通知由谁发布

不同类型的信息由对应负责人主导。

| 信息 | 主要发布负责人 |
|---|---|
| 项目整体规则 | Project Lead |
| 人员确认 | People & Scheduling |
| Availability | People & Scheduling |
| 正式排班 | People & Scheduling |
| 培训安排 | People & Scheduling / 指定培训负责人 |
| 集合要求 | Operations |
| 岗位安排 | Operations |
| 现场调度 | Operations |
| 重大项目调整 | Project Lead |
| 跨模块重大通知 | Project Lead |

协助人可以代为发送。

但正式内容必须先与 Owner 对齐。

---

## 十一、避免多人重复发布正式信息

三位负责人不应分别发布三个不同版本。

不推荐：

    负责人 A：
    08:00 集合

    负责人 B：
    好像 08:30

    负责人 C：
    我听说 08:15

遇到未确认信息时，应使用：

> `TBD / 待确认`

而不是猜测。

确认后由对应 Owner 发布正式版本。

---

## 十二、如果负责人之间出现不同意见

如果三位负责人对某项信息理解不同：

    发现冲突
       ↓
    暂停发布新的正式版本
       ↓
    对应模块 Owner 核实
       ↓
    必要时 Project Lead 协调
       ↓
    形成唯一结论
       ↓
    更新 GitHub
       ↓
    发布正式通知

原则：

> **先解决管理层内部冲突，再向志愿者发布。**

尽量避免把管理层内部讨论直接丢给普通志愿者判断。

---

## 十三、如果志愿者收到互相冲突的指令

如果不同负责人给出不同安排：

### 非紧急情况

成员应：

    暂停执行有冲突的部分
          ↓
    向直接负责人确认
          ↓
    必要时升级 Project Lead
          ↓
    获得唯一明确安排

### 现场紧急情况

优先：

- 保证人员安全
- 保证大会现场基本秩序
- 按当值现场负责人最新明确指令执行

情况稳定后再确认正式记录。

---

## 十四、排班变更沟通流程

如果成员无法参加已经发布的正式排班：

    成员尽早通知
          ↓
    People & Scheduling 确认
          ↓
    Operations 判断岗位影响
          ↓
    是否需要替补 / 调岗
          ↓
    形成新方案
          ↓
    更新 GitHub
          ↓
    通知相关成员
          ↓
    成员确认收到

后续 Issue 模板建立后，重要排班变化使用：

`[排班调整]`

记录。

不能只在群聊中说：

> “你和他换一下。”

然后不更新正式排班。

---

## 十五、岗位变化沟通流程

现场岗位出现变化时：

    Operations 判断需要调整
          ↓
    明确被调整成员
          ↓
    明确新岗位 / 新区域
          ↓
    明确直接负责人
          ↓
    通知成员
          ↓
    确认成员理解
          ↓
    必要时更新正式记录

短时间临时支援可以不修改正式排班。

实质性岗位变化应记录。

---

## 十六、紧急问题沟通原则

对于紧急问题：

> **不要先开 Issue 再等回复。**

优先：

    直接联系现场负责人
          ↓
    立即处理
          ↓
    必要时升级 Project Lead
          ↓
    必要时联系大会对应负责人
          ↓
    情况稳定
          ↓
    补充记录

典型紧急情况包括：

- 人员安全问题
- 明显现场安全风险
- 重要岗位突然无人
- 大范围人员缺口
- 严重秩序问题
- 影响大会正常运行的问题
- 需要大会方立即处理的问题

---

## 十七、问题升级路径

正常升级路径：

    志愿者
       ↓
    直接负责人
       ↓
    Operations / People & Scheduling
       ↓
    Project Lead
       ↓
    大会对应负责人

不是所有问题都需要直接找 Project Lead。

---

## 十八、人员类问题找谁

以下问题优先找：

> **People & Scheduling**

包括：

- GitHub Username
- Volunteer ID
- GitHub 邀请
- 入组状态
- 培训状态
- Availability
- 无法参加
- 请假
- 换班
- 排班疑问
- 人员状态错误

---

## 十九、现场类问题找谁

以下问题优先找：

> **Operations**

包括：

- 集合地点
- 到场后找谁
- 岗位是什么
- 工作区域
- 现场缺人
- 临时调岗
- 物料
- 签到
- 签退
- 现场异常
- 工作结束时间
- 加班现场确认

---

## 二十、项目级问题找谁

以下问题优先升级：

> **Project Lead**

包括：

- 三位负责人无法形成一致方案
- 跨模块重大冲突
- 大规模人员不足
- 关键岗位持续无人
- 大会方重大需求变化
- 影响整个项目的风险
- 重大现场问题
- 项目规则需要修改

---

## 二十一、确认收到

重要通知不应只发送，不确认。

对于以下信息建议要求相关成员确认：

- FINAL 排班
- 集合时间
- 集合地点
- 岗位安排
- 临时正式换班
- 重大现场安排变化

可以使用简单回复：

> 收到

或：

> 已确认

负责人重点关注：

> 有没有人没有确认。

而不是要求所有普通通知都必须回复。

---

## 二十二、群聊中的 @ 使用原则

建议只在确实需要相关人员注意时使用 @。

例如：

- 当天正式排班人员
- 尚未确认 Availability 的成员
- 某项任务的 Owner
- 需要立即回应的负责人

不要所有信息都：

> @所有人

否则容易产生信息疲劳。

重要程度越高，通知对象越应该精准。

---

## 二十三、减少重复沟通

如果某个问题已经有正式文档，应优先发送链接。

例如志愿者问：

> “我什么时候算 READY？”

可以回复：

> 请查看 `roster/volunteer-status.md` 中的 READY 判定标准。

而不是每次重新解释一个不同版本。

这样可以减少规则漂移。

---

## 二十四、GitHub Issue 与群聊的区别

### 群聊适合

- 快速提问
- 临时协调
- 实时通知
- 紧急问题
- 简单确认

### Issue 适合

- 需要明确 Owner
- 需要持续跟踪
- 需要截止时间
- 需要多人协作
- 需要形成处理闭环
- 需要以后追溯

例如：

> “我不知道 GitHub 怎么进。”

可以先群里问。

如果经过处理仍无法解决，可以创建：

`[支持请求] 无法访问项目仓库`

---

## 二十五、重要决定回写 GitHub

如果群聊中形成：

> “最终就这么定。”

负责人应判断是否属于正式信息。

如果是，则执行：

    群聊讨论
       ↓
    形成最终结论
       ↓
    对应 Owner 更新 GitHub
       ↓
    必要时群内通知
       ↓
    后续统一以 GitHub 为准

这是本项目非常重要的管理原则。

---

## 二十六、什么情况下必须回写

以下变化原则上必须回写：

- 正式排班改变
- 正式岗位改变
- 工作日期改变
- 集合时间重大改变
- 集合地点改变
- 正式负责人改变
- 成员无法到岗
- 替补人员正式加入
- 重要项目规则改变
- 重大现场异常结果
- 影响后续工作的正式决定

---

## 二十七、沟通中的 TBD

尚未确认的信息统一使用：

`TBD`

或：

> 待确认

例如：

    集合地点：TBD

比：

> “应该是在 A 门吧”

更加可靠。

当信息确认后，再更新正式版本。

---

## 二十八、敏感信息沟通

以下信息原则上不要发送到 GitHub，也不要发送到大型群聊：

- 身份证号码
- 身份证照片
- 银行卡
- 收款账户
- 家庭住址
- 账号密码
- 验证码
- 详细医疗信息
- 内部筛选评价
- 其他不必要的个人隐私

确实需要处理时，使用项目指定的受控渠道。

---

## 二十九、志愿者个人问题

如果成员遇到私人原因影响工作：

不需要向整个群解释详细原因。

只需要向对应负责人提供执行安排所需要的信息。

例如：

> “我 9 月 7 日无法参加，需要调整排班。”

通常已经足够用于项目管理。

如果负责人确实需要进一步了解，应私下沟通。

---

## 三十、负责人交接沟通

如果某负责人当天无法继续处理自己的职责，应进行交接。

交接至少包含：

- 当前未完成事项
- 当前重要风险
- 哪些成员需要继续跟进
- 哪些 Issue 尚未处理
- 哪些现场安排待确认
- 临时接手负责人

推荐格式：

    交接角色：
    Operations

    原负责人：
    TBD

    临时负责人：
    TBD

    未完成事项：
    TBD

    当前风险：
    TBD

    下一步：
    TBD

---

## 三十一、活动前沟通节奏

筹备阶段重点沟通：

    人员
      ↓
    GitHub 入组
      ↓
    培训
      ↓
    Availability
      ↓
    排班
      ↓
    岗位
      ↓
    集合
      ↓
    READY

越接近活动日期，应逐渐减少：

> “还不知道。”

最终让所有重要执行信息进入确定状态。

---

## 三十二、活动当天沟通节奏

每天开始前：

- 确认人员
- 确认集合
- 确认签到
- 确认岗位
- 确认直接负责人
- 确认当天特殊事项

活动进行中：

- 现场调度
- 岗位支援
- 人员状态
- Incident
- Escalation

活动结束：

- 签退
- 实际工作时间
- 加班
- 异常
- 交接
- 第二天调整事项

---

## 三十三、重要事项沟通检查

发布重要信息前，负责人可以快速检查：

- [ ] 信息是否已经确认
- [ ] 是否明确适用人员
- [ ] 是否包含日期
- [ ] 是否包含时间
- [ ] 是否包含地点
- [ ] 是否明确需要执行的动作
- [ ] 是否明确负责人
- [ ] 是否需要 GitHub 正式记录
- [ ] 是否需要相关成员确认收到

---

## 三十四、负责人内部沟通原则

三位负责人内部应遵循：

> **问题内部先对齐，正式版本统一发布。**

避免：

- 同一个问题多个版本
- 未确认信息提前对外发布
- 在志愿者群里公开争论管理方案
- 出现问题后互相等待
- 多人都以为别人会处理

每个问题仍然遵循：

> **One Task, One Owner**

---

## 三十五、最终沟通规则

整个项目采用以下基本逻辑：

    普通沟通
       ↓
    即时通讯

    正式信息
       ↓
    GitHub

    紧急现场问题
       ↓
    直接联系负责人

    需要持续跟踪的问题
       ↓
    Issue

    群聊形成正式决定
       ↓
    回写 GitHub

---

## 三十六、Communication READY

在活动开始前，应保证每名正式志愿者都清楚：

- [ ] 正式信息在哪里查看
- [ ] 群聊主要用于什么
- [ ] GitHub 主要用于什么
- [ ] 人员问题找谁
- [ ] 现场问题找谁
- [ ] 重大问题找谁
- [ ] 紧急情况不能等待 Issue
- [ ] 排班以最新 FINAL 为准
- [ ] 正式变化会同步 GitHub
- [ ] 不应在公共渠道发送敏感信息

三位负责人同时需要做到：

- [ ] 正式通知来源明确
- [ ] 不发布互相冲突的信息
- [ ] 群聊重大决定及时回写
- [ ] 重要通知确认成员已收到
- [ ] 每个需要处理的问题都有 Owner
- [ ] 紧急问题有清晰升级路径

全部满足后：

> **Communication System：READY**
