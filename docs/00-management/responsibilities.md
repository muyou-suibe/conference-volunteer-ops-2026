# 项目负责人职责与分工

本文件用于明确 2026 大会志愿者项目三名负责人的职责、权限、协作边界和问题升级机制。

项目管理的核心原则：

> **One Task, One Owner**
>
> 一项任务可以有多人协助，但必须只有一名主要负责人。

---

## 一、管理团队

本项目由 3 名负责人共同管理。

| 管理角色 | 人员 | GitHub | 核心职责 |
|---|---|---|---|
| Project Lead / 项目统筹 | 负责人 A | TBD | 总体进度、关键决策、跨模块协调 |
| People & Scheduling / 人员与排班 | 负责人 B | TBD | 人员、入组、培训状态、Availability、排班 |
| Operations / 现场运营 | 负责人 C | TBD | 岗位、会场、签到签退、现场调度、异常处理 |

> 以上角色为当前推荐分工。
>
> 三位负责人最终确认后，可以根据实际情况调整人员，但应尽量保持职责边界稳定。

---

## 二、负责人 A：Project Lead / 项目统筹

### 1. 核心目标

保证整个志愿者项目按照计划推进，并确保：

- 重要事项有人负责
- 关键任务有截止时间
- 项目风险有人跟踪
- 跨模块问题有人协调
- 重大决定有明确结果
- 正式决定能够回写 GitHub

### 2. 主要职责

负责人 A 主要负责：

- 维护 GitHub 项目的整体结构
- 管理项目总体时间线
- 明确三位负责人职责
- 检查重要任务是否存在明确 Owner
- 跟踪关键任务进度
- 组织重要项目决策
- 处理跨模块问题
- 协调人员、排班与现场运营之间的冲突
- 检查项目关键阻塞项
- 组织活动前最终 READY Review
- 组织每日关键问题复盘
- 组织项目结束后的整体复盘

### 3. 重点关注

负责人 A 主要回答以下问题：

    项目整体是否可执行？
            ↓
    是否存在无人负责的任务？
            ↓
    是否存在影响活动的阻塞项？
            ↓
    是否需要负责人之间协调？
            ↓
    是否存在必须立即决策的问题？

### 4. 不建议承担

Project Lead 不应成为：

> “所有事情最后都找的人。”

日常人员问题优先由负责人 B 处理。

日常现场执行问题优先由负责人 C 处理。

只有以下情况再升级至 Project Lead：

- 跨模块冲突
- 重大人员问题
- 重大排班问题
- 现场重大异常
- 无法由单一负责人解决的问题
- 可能影响大会正常运行的问题

---

## 三、负责人 B：People & Scheduling / 人员与排班

### 1. 核心目标

确保需要参加活动的人：

> 人数正确、状态清楚、日期明确、排班明确。

### 2. 主要职责

负责人 B 负责：

- 确认正式志愿者名单
- 收集 GitHub Username
- 分配 Volunteer ID
- 跟踪 GitHub 加入状态
- 跟踪入组完成情况
- 跟踪培训完成情况
- 收集志愿者 Availability
- 检查每日可参与人数
- 编制正式排班
- 维护正式排班状态
- 处理迟到、请假、无法到岗等人员问题
- 处理排班变更
- 协调替补人员
- 跟踪成员 READY 状态
- 配合现场负责人进行人员调度

### 3. 主要维护文件

负责人 B 主要维护：

`roster/volunteer-status.md`

用于：

> 跟踪成员整体准备状态。

以及：

`roster/availability.md`

用于：

> 记录每位成员哪些日期可以参加。

以及：

`docs/03-schedule/`

用于：

> 管理最终正式排班。

### 4. 负责人 B 需要回答的问题

    20 名正式志愿者确定了吗？

    谁加入 GitHub 了？

    谁完成入组了？

    谁完成培训了？

    谁哪一天可以参加？

    谁哪一天被正式安排？

    当天人数够不够？

    有没有人临时不能来？

    有没有替补方案？

### 5. 人员信息管理原则

GitHub 中只保存项目所需的非敏感信息。

允许记录：

- Volunteer ID
- GitHub Username
- 入组状态
- 培训状态
- Availability
- 正式排班
- 岗位状态
- 出勤确认状态

不得在仓库中保存：

- 身份证号码
- 身份证照片
- 银行卡信息
- 收款账户
- 家庭住址
- 详细健康信息
- 候选人内部评分
- 淘汰原因
- 其他不必要的隐私信息

## 四、负责人 C：Operations / 现场运营

### 1. 核心目标

确保活动现场每名志愿者都清楚：

> 去哪里、做什么、找谁、出了问题怎么办。

### 2. 主要职责

负责人 C 负责：

- 确认现场岗位需求
- 定义岗位职责
- 确认工作区域
- 确认集合地点
- 确认集合流程
- 制定签到流程
- 制定签退流程
- 确认当日岗位分配
- 负责现场人员调度
- 负责临时调岗
- 管理机动人员
- 确认现场物料准备
- 处理现场异常
- 管理问题升级流程
- 确认实际工作结束时间
- 确认符合条件的加班情况
- 组织当天运营复盘

### 3. 主要维护目录

负责人 C 主要维护：

`docs/04-roles/`

用于：

> 岗位说明和岗位职责。

以及：

`docs/05-operations/`

用于：

> 签到签退、调岗、异常、升级、加班等现场 SOP。

### 4. 负责人 C 需要回答的问题

    志愿者到哪里集合？

    几点到？

    到了以后找谁？

    每个人做什么？

    岗位在哪里？

    工作区域在哪里？

    现场缺人怎么办？

    有人迟到怎么办？

    有人临时离岗怎么办？

    出现异常找谁？

    什么情况下需要升级？

    什么时候算工作结束？

## 五、职责边界

| 事项 | 主要负责人 |
|---|---|
| GitHub 项目总体结构 | Project Lead |
| 项目总体进度 | Project Lead |
| 关键项目决策 | Project Lead |
| 跨模块协调 | Project Lead |
| 正式志愿者状态 | People & Scheduling |
| GitHub Username | People & Scheduling |
| Volunteer ID | People & Scheduling |
| Availability | People & Scheduling |
| 培训完成状态 | People & Scheduling |
| 正式排班 | People & Scheduling |
| 排班人员变更 | People & Scheduling |
| 岗位设计 | Operations |
| 集合地点 | Operations |
| 集合流程 | Operations |
| 现场分组 | Operations |
| 签到签退 | Operations |
| 现场调岗 | Operations |

## 六、One Task, One Owner

所有重要任务必须明确一个 Owner。

推荐方式：

    任务：
    确认 9 月 6 日正式志愿者名单

    Owner：
    负责人 B

    协助：
    负责人 A

不推荐：

    负责人：
    A / B / C 大家一起处理

原因：

> 多人可以共同参与，但必须明确谁对最终结果负责。

### Owner 的基本责任

任务 Owner 应负责：

- 明确任务目标
- 推动任务执行
- 协调需要的协助人员
- 发现阻塞及时反馈
- 更新 GitHub 状态
- 确认最终结果

---

## 七、负责人之间的协作方式

### 普通问题

    问题产生
       ↓
    对应模块负责人处理
       ↓
    问题解决
       ↓
    必要时更新 GitHub 正式记录

### 跨模块问题

例如：

> 某名志愿者临时无法参加，同时影响某个关键岗位。

处理方式：

    People & Scheduling
            +
        Operations
            ↓
        协商方案
            ↓
    必要时 Project Lead 决策
            ↓
      更新正式记录

---

## 八、问题升级机制

### Level 1：普通问题

例如：

- 不会使用 GitHub
- 培训资料找不到
- 不清楚自己的安排
- 不知道某份文档在哪里

由对应模块负责人处理。

### Level 2：影响排班或岗位的问题

例如：

- 志愿者临时无法参加
- 志愿者迟到
- 岗位临时缺人
- 需要换班
- 需要临时调岗
- Availability 突然发生变化

由：

> People & Scheduling + Operations

共同处理。

### Level 3：重大问题

例如：

- 大面积人员不足
- 重要岗位无人值守
- 严重现场异常
- 明显安全风险
- 重要嘉宾相关重大问题
- 可能影响大会正常运行的问题

立即升级：

    Operations / People
            ↓
        Project Lead
            ↓
      大会对应负责人

## 九、GitHub 与即时通讯的分工

### GitHub 用于

保存正式信息：

- 项目任务
- 负责人
- 正式文档
- 培训资料
- Availability
- 排班
- 岗位
- SOP
- 状态
- 变更记录
- 异常记录
- 项目复盘

### 即时通讯用于

处理实时沟通：

- 临时通知
- 集合提醒
- 实时协调
- 临时人员调度
- 紧急问题
- 活动现场快速沟通

核心原则：

> 即时通讯解决速度问题，GitHub 解决记录和协作问题。

如果微信群、私聊或现场口头讨论形成正式决定，应同步更新 GitHub。

## 十、重大事项确认

以下事项原则上不能由普通志愿者自行决定：

- 改变正式排班
- 自行换班
- 调整重要岗位
- 擅自离岗
- 取消某成员的正式工作安排
- 增减正式人员
- 修改集合时间
- 修改工作地点
- 修改正式工作时间
- 确认重大加班
- 对外作出重要承诺

应由对应负责人确认。

---

## 十一、活动筹备阶段管理节奏

活动前，三位负责人定期检查：

    人员确认
       ↓
    GitHub 入组
       ↓
    培训
       ↓
    Availability
       ↓
    正式排班
       ↓
    岗位
       ↓
    现场准备
       ↓
    风险检查
       ↓
    READY Review

重点关注：

- 是否存在未确认成员
- 是否存在培训未完成成员
- 每日人数是否满足需求
- 是否存在排班冲突
- 是否存在岗位未明确
- 是否存在重要 TBD
- 是否存在阻塞项

---

## 十二、活动期间每日管理节奏

### 每天开始前

三位负责人确认：

- [ ] 当日人员是否满足需求
- [ ] 志愿者是否到齐
- [ ] 所有岗位是否明确
- [ ] 所有区域是否明确
- [ ] 每名成员是否知道自己的负责人
- [ ] 集合是否完成
- [ ] 签到是否完成
- [ ] 现场物料是否准备完成
- [ ] 是否存在人员缺口
- [ ] 是否存在未解决风险

### 活动进行中

重点处理：

- 人员状态
- 岗位状态
- 临时调岗
- 现场异常
- 人员缺口
- 重要沟通
- 升级问题

### 每天结束后

确认：

- [ ] 签退完成
- [ ] 实际工作时间确认
- [ ] 加班情况确认
- [ ] 当日异常已记录
- [ ] 未完成事项已交接
- [ ] 第二天需要调整的问题已明确

---

## 十三、负责人交接原则

如果某负责人暂时无法继续处理其职责，应明确交接给另一名负责人。

不能出现：

> “我今天不在，所以没人管。”

交接至少说明：

- 当前未完成事项
- 重要联系人
- 当前风险
- 待确认事项
- 下一步行动
- 临时接手负责人

---

## 十四、管理信息状态

管理层的重要信息建议统一使用：

| 状态 | 含义 |
|---|---|
| TBD | 尚未确定 |
| 待开始 | 尚未开始 |
| 进行中 | 正在处理 |
| 等待中 | 等待外部信息或其他任务 |
| 已完成 | 工作完成 |
| BLOCKED | 当前存在阻塞 |
| READY | 已达到执行条件 |

## 十六、最终原则

本项目负责人团队应遵循：

> 有任务，就有 Owner。  
> 有变化，就有记录。  
> 有问题，就有升级路径。  
> 有决定，就同步正式信息。  
> 有现场执行，就必须有人负责。

最终目标不是增加管理流程，而是确保：

> **20 名志愿者能够在 3 名负责人的协调下稳定、有序地完成大会现场工作。**
