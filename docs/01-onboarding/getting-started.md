# 志愿者入组指南

欢迎加入 2026 大会志愿者项目。

本指南适用于已经正式确认参与本次大会现场志愿服务的成员。

完成本指南所要求的入组事项后，项目负责人将根据实际完成情况更新你的项目状态。

最终活动前状态为：

> **READY（准备完成）**

---

## 一、入组流程

正式志愿者按照以下流程完成项目准备：

    确认参加
        ↓
    提交 GitHub Username
        ↓
    分配 Volunteer ID
        ↓
    获得项目访问权限
        ↓
    完成入组
        ↓
    完成培训
        ↓
    确认 Availability
        ↓
    确认正式排班
        ↓
    确认岗位
        ↓
    READY

请按照本指南逐项完成。

---

## 二、确认 GitHub 访问权限

请首先确认：

- 可以正常登录 GitHub
- 使用的是准备参与本项目的 GitHub 账号
- 可以访问项目仓库
- 可以正常查看项目 README
- 可以正常查看 `docs/` 目录
- 可以正常查看 `roster/` 中允许访问的项目协作信息

项目仓库：

`conference-volunteer-ops-2026`

如果无法访问，请联系项目负责人。

不要因为无法访问而重复创建多个 GitHub 账号。

---

## 三、确认 GitHub Username

每位志愿者需要向负责人提供自己的 GitHub Username。

例如：

`@username`

请注意：

> GitHub Username 与昵称、Display Name 不一定相同。

请以个人 GitHub 主页地址中的用户名为准。

例如：

    github.com/example-user

对应 GitHub Username：

    example-user

负责人确认后，会把 Username 与 Volunteer ID 对应。

---

## 四、确认 Volunteer ID

每位正式志愿者获得唯一的 Volunteer ID。

统一格式：

    V001
    V002
    V003
    ...
    V020

Volunteer ID 用于项目内部：

- 成员状态管理
- Availability
- 培训确认
- 排班
- 岗位分配
- 出勤确认
- 异常记录
- 项目复盘

Volunteer ID 不等于真实姓名。

如果发现自己的 Volunteer ID 与负责人通知不一致，应及时确认。

## 六、确认 Availability

活动日期：

| 日期 | 当日需求人数 |
|---|---:|
| 9 月 6 日 | 4 人 |
| 9 月 7 日 | 8 人 |
| 9 月 8 日 | 20 人 |
| 9 月 9 日 | 20 人 |

成员需要确认自己每一天是否可以参加。

Availability 状态统一使用：

| 标记 | 含义 |
|---|---|
| ✅ | 可以参加 |
| ❌ | 无法参加 |
| ❓ | 尚未确认 |
| ⚠️ | 有条件参加，需要与负责人确认 |

Availability 表：

[`roster/availability.md`](../../roster/availability.md)

必须理解：

    Availability
    = 我这一天能不能参加

    Schedule
    = 项目负责人最终有没有安排我工作

因此：

> 可以参加，不等于已经正式排班。

例如某天只需要 4 人，即使有 15 人可以参加，也不会安排全部 15 人。

## 八、确认正式排班

正式排班统一存放在：

`docs/03-schedule/`

排班总则：

[`docs/03-schedule/README.md`](../03-schedule/README.md)

正式排班至少会明确：

| 信息 | 说明 |
|---|---|
| Volunteer ID | 志愿者编号 |
| GitHub Username | GitHub 用户名 |
| 日期 | 工作日期 |
| 岗位 | 当日岗位 |
| 区域 | 工作区域 |

| 状态 | 含义 |
|---|---|
| DRAFT | 草案 |
| REVIEW | 负责人确认中 |
| FINAL | 正式版本 |
| CLOSED | 当日工作结束并归档 |

只有：

> **FINAL**

状态的排班才作为正式工作安排。

## 九、确认岗位

岗位说明统一存放在：

`docs/04-roles/`

大会方明确具体岗位后，项目负责人会发布正式岗位说明。

岗位可能根据现场实际需求设置。

被分配岗位后，至少需要确认：

- 我的岗位是什么
- 我的工作区域在哪里
- 我的主要任务是什么
- 我的工作时间是什么
- 我的直接负责人是谁
- 哪些事情我可以自行处理
- 哪些事情必须上报
- 岗位需要如何交接

不要只知道：

> “我今天来做志愿者。”

而不知道自己的具体职责。

## 十、了解三位负责人分工

负责人职责说明：

[`docs/00-management/responsibilities.md`](../00-management/responsibilities.md)

项目原则：

> **One Task, One Owner**

一般情况下：

- 人员、Availability、排班相关问题 → 人员与排班负责人
- 岗位、签到签退、现场执行问题 → 现场运营负责人
- 跨模块、重大或无法解决的问题 → Project Lead

不要所有事情都直接找同一个负责人。

---

## 十一、了解 GitHub 与即时通讯的区别

### GitHub 用于

保存正式项目记录，包括：

- 项目规则
- 培训资料
- Availability
- 正式排班
- 岗位说明
- SOP
- 正式变更
- Issue
- 异常记录
- 项目复盘

### 即时通讯用于

处理：

- 实时通知
- 集合提醒
- 临时协调
- 现场调度
- 紧急问题

核心原则：

> GitHub 是正式记录。  
> 即时通讯负责实时沟通。

如果微信群、私聊或口头通知形成正式调整，负责人会根据需要同步回 GitHub。

---

## 十二、了解问题升级流程

正常问题升级路径：

    志愿者
       ↓
    岗位 / 区域负责人
       ↓
    当值项目负责人
       ↓
    Project Lead
       ↓
    大会对应负责人

遇到以下情况应及时报告：

- 无法按时到岗
- 可能迟到
- 无法参加正式排班
- 需要提前离岗
- 身体原因无法继续工作
- 岗位出现人员缺口
- 岗位无人值守
- 不清楚应该如何处理参会者需求
- 嘉宾相关问题超出处理权限
- 设备或网络异常
- 现场秩序异常
- 安全风险
- 其他可能影响活动正常运行的问题

紧急问题：

> 优先联系现场负责人，不要等待 GitHub Issue 回复。

问题稳定后，再根据实际需要形成正式记录。

## 十三、活动当天执行流程

活动当天基本流程：

    按要求到达集合地点
            ↓
          签到
            ↓
        负责人点名
            ↓
        确认当天岗位
            ↓
        确认工作区域
            ↓
        开始现场工作
            ↓
    临时调岗 / 支援（如有）
            ↓
          岗位交接
            ↓
          签退
            ↓
      加班确认（如有）

未经负责人确认：

- 不应擅自离岗
- 不应自行换岗
- 不应自行换班
- 不应自行修改工作时间
- 不应对外作出超出职责范围的重要承诺

---

## 十四、签到与签退

正式签到签退制度后续统一存放在：

`docs/05-operations/check-in-check-out.md`

基本原则：

> 排班记录回答“谁应该来”。

> 签到签退记录回答“谁实际来了、实际工作到什么时候”。

因此排班不能代替考勤。

如果迟到、请假或无法到岗，应第一时间联系负责人。

---

## 十五、工作时间与加班

原则上每日工作约：

**8 小时**

具体时间以当天正式排班为准。

正常工作报酬：

**300 元 / 天**

如实际工作产生符合项目规定的加班，应按照项目加班确认流程处理。

志愿者不应自行认定最终加班时长或结算结果。

GitHub 中只记录必要的项目确认状态。

银行卡、收款账户等敏感财务信息不在本仓库中管理。

---

## 十六、现场行为基本要求

所有志愿者应：

- 按要求准时到达
- 遵守现场纪律
- 保持适当仪表
- 使用礼貌、清晰的沟通方式
- 对参会者保持耐心
- 遇到不知道的问题及时求助
- 按岗位要求完成交接
- 服从合理的现场调度
- 保护项目内部信息和个人隐私

不要：

- 擅自离岗
- 擅自换班
- 擅自改变重要现场安排
- 对不确定的信息随意回答
- 对外作出未经授权的重要承诺
- 在 GitHub 中上传敏感个人信息

遇到无法回答的问题时，可以明确说明需要向负责人确认。

---

## 十七、信息安全

本仓库可以记录项目协作所需信息，例如：

- Volunteer ID
- GitHub Username
- Availability
- 培训状态
- 排班状态
- 岗位
- 出勤确认状态

不要在 GitHub 中提交：

- 身份证号码
- 身份证照片
- 银行卡信息
- 收款账户
- 家庭住址
- GitHub 密码
- 其他账号密码
- 短信验证码
- 不必要的完整联系方式
- 详细医疗信息
- 其他敏感个人信息

涉及个人健康问题时，只向负责人说明完成工作安排所必要的信息即可。

只有完成以下事项，成员才能进入 `READY`：

- [ ] GitHub 账号正常
- [ ] 项目仓库访问正常
- [ ] GitHub Username 已确认
- [ ] Volunteer ID 已确认
- [ ] README 已阅读
- [ ] Availability 已确认
- [ ] 入组要求已完成
- [ ] 必要培训已完成
- [ ] 正式排班已确认
- [ ] 当日岗位已确认
- [ ] 集合时间和地点已知晓
- [ ] 对应负责人已知晓
- [ ] 现场沟通方式已知晓
- [ ] 异常升级方式已知晓

完成全部活动前准备后：

> **READY**

表示该成员已经具备进入现场执行阶段的条件。

---

## 十九、发现信息错误怎么办

如果发现以下信息存在错误：

- GitHub Username
- Volunteer ID
- Availability
- 培训状态
- 排班
- 岗位
- 其他项目状态

不要直接修改其他成员的数据。

应联系对应负责人。

后续 Issue 系统上线后，也可以根据问题类型使用：

`[支持请求]`

或：

`[排班调整]`

提交需要处理的问题。

## 二十、入组完成后的下一步

完成本指南要求后，项目流程继续进入：

    入组完成
       ↓
    培训完成
       ↓
    Availability 确认
       ↓
    正式排班
       ↓
    岗位确认
       ↓
    READY
       ↓
    现场执行

如果当前某项信息仍然显示 `TBD` 或“待确认”，不代表出现错误。

它表示：

> 对应事项仍需要项目负责人进一步确认。

请关注 GitHub 中的正式更新和负责人通知。
